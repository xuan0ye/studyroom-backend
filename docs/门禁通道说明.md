## 2. 完整链路

```
① 设备自举（设备 → 我们）
   设备每 5.5 秒轮询 POST  http(s)://<我们的域名>/server/access
       请求体: {"access_mac":"8002F432050F","access_type":"0A05","factory":"act"}
   我们应答 442 字节: code / mqtt_addr / mqtt_port / device_id / device_secret
                     / mqtt_clientId / mqtt_sub / mqtt_pub / mqtt_ping_cli / mqtt_ping_svr
                     / http_svr / qr_url
   ※ 拿到配置后设备不再轮询；只有开机或配置失效时才会再次自举

② 设备连 broker（设备 ↔ 我方 mosquitto）
   clientId = 设备 SN(8002F432050F)，账号 studyroom，keepalive 120
   订阅: iot/cli/0A05/<SN>/eth  +  iot/cli/FFFF/<SN>/eth
   上报: iot/svr/...

③ 命令下发（后端 → 设备）
   DeviceMqttChannel → iot/cli/0A05/<SN>/eth（另发 FFFF 兼容），明文 JSON 的 action 报文
```

## 3. 我们下发的人员信息（**可用**）

| action | 关键字段 | 设备回执 |
|---|---|---|
| `read_user` | `user_id=0, page, size` | `data[]`（用于查重、对账） |
| `add_user` | `user_acct=__sr<userId>`、`user_name`、`auth_mark=240`、`auth_group=0`、`floor=FFFFFFFFFFFFFFFF`、`exp_opt=<到期秒>`、`exp_start=0`、`user_type=32` | `data[0].user_id` |
| `add_face` | `user_id` + `data[{id:"0", type:"jpg", d:<base64 JPG>}]` | `code:"0"`=成功；`code:"1"`=人脸检测未过 |
| `del_face` | `user_id` | `code:"0"` |
| `del_user` | `user_acct` | `code:"0"` |

**三个必须知道的坑**（代码注释里也有，别再踩）：

1. `add_user` 每调用一次就在设备上**新建一个人**。必须先 `read_user` 按账号查重、复用 `user_id`，否则同一个人堆出多个账号，撤销时只删掉一个，**剩下的还能刷开设备**。
2. 对**已经有人脸**的用户再 `add_face` 会被直接拒绝（`code:"1"`）。必须先 `del_face` 再下发，否则用户永远改不了照片。
3. `code:"1"` 是**设备端人脸检测没过**（太糊 / 太暗 / 侧脸 / 遮挡），不是网络问题，重传前先换照片。

**账号规则**：我们建的人 `user_acct = __sr<userId>`，可按前缀反解回小程序用户，用于后台对账。

## 4. 做不到的两件事（**不要再投入时间**）

### 4.1 远程开门 —— 不可行

- 厂商文档里的 `F1openDoor` 属于 `protocolVersion=1`（标准协议），本机是 `protocolVersion=0`（时之盾私有协议）。
- 实测：发到设备真正订阅的 `iot/cli/.../eth` → 回 `code:"7"`（不认该动作）；发到 `cs/<SN>/csmsg` → 回 `code:"2"`（解析失败），且设备**从未订阅过 `cs/`**。
- 厂家 App 能开门，是因为它走时之盾协议的**加密信封** `{"code":"<不透明签名串>"}`，密钥在厂家手里。

### 4.2 通行记录 —— 不可行

- `read_record` 在这台设备上**不是"服务器来读"的动作，而是"设备主动往上推送"的动作**（厂商 broker 流量里它 31 次全是推送）。
- 我们接管后：设备 3 小时内 **0 条非心跳报文**；标准协议的 HTTP `url/upRecord` **一次都没来**；`read_record` 反向读回 `code:"2"`。
- 设备自己的 `open_door` 事件里**不带用户身份**（无 `user_acct` / `jobnumber`），就算收到也认不出是谁。

**替代方案（已上线）**

- 开 门：继电器并联到门禁机"出门按钮"的干接点 → `studyroom.door.open-url`
- 签 到：顾客到座位点「开灯」即签到 → `studyroom.checkin.light-on-enabled=true`（锁座卡也覆盖，见 `ensureTodayRecordForLockedSeat`）

## 5. ⚠️ 绝对不要动（动了现场就失联）

按危险程度排序：

1. **设备端「通信设置 → 服务器地址」**：必须保持指向我们的服务器。改回厂家 = 我们**彻底失去这台设备**；而且厂家后台已不再管理它，`qr_url` 里那个 `access.yefiot.com/act?c=<SN>` 录脸二维码**现在实际走不通**，别再当备用通道用。
2. `studyroom.access.bootstrap.enabled` 必须是 `true`。关掉后设备开机自举拿不到配置 → 连不上 broker → 所有下发失效。
3. `studyroom.access.mqtt.public-host` / `public-port`：必须是**设备能访问到**的地址（当前 `101.133.152.241:1883`）。填成内网或容器地址，设备就会连不上。
4. `studyroom.access.mqtt.username` / `password`：这是**设备登录 MQTT 的账号**。改了之后设备仍然用旧账号，会被 broker 拒绝，**必须到现场改设备**——所以不要改。
5. `studyroom.access.mqtt.cmd-topic=both`（eth + cs 都发）；`studyroom.access.device-protocol=action`（本机 protocolVersion=0，不能填 standard）。
6. Redis 覆盖键 `studyroom:access:bootstrap:reply` 和 `studyroom:access:login:reply`：只用于不停机试协议。**设错了设备下次自举会拿到坏配置而失联** → 试完必须 DEL 清掉：
   ```bash
   redis-cli DEL studyroom:access:bootstrap:reply studyroom:access:login:reply
   ```
7. 不要关 mosquitto、不要改 1883 端口、不要换 broker。
8. 不要打开 `studyroom.door.mqtt-open-enabled`：打开只会让"一键开门"按钮出现、点了却失败，比不显示更糟。

## 6. 可用性要求

- **重启 `studyroom` 后端：安全**。设备连的是 mosquitto，不是后端，长连接不受影响，只是后端暂时不发命令。
- 重启 mosquitto / 整机重启：设备会自己重连（它现在固定连我们）。
- 服务器长时间不可达：设备重连失败 → 新录脸、撤销、开门全部失效，需恢复网络或现场重启设备。

## 8. 换设备时怎么恢复"刷脸签到 + 远程开门"

只有**换设备**（或让厂家把固件协议改掉）才行。新设备必须同时满足：

1. 系统参数 `protocolVersion=1`（标准协议）；
2. 会订阅 `cs/<SN>/csmsg`，命令是明文 `F1*`（不需要厂家签名）；
3. 支持 HTTP `url/upRecord` 记录上报，并允许把 `url` 指向我们；
4. 或：厂家提供开放 API / 密钥。

满足后要改的三处：

```
studyroom.access.device-protocol: standard
studyroom.checkin.light-on-enabled: false        # 切回刷脸签到
studyroom.door.mqtt-open-enabled: true           # 放开服务器开门口令
```

并把设备服务器地址指向我们的 `/access/login`（或 `server/login` / `serve/login` 别名）。

## 9. 隐私与数据留存

- 人脸照片**不落库**：`sr_access_profile` 不保存 `face_photo_base64` / `face_photo_url`，照片只在内存中透传给设备、存进设备本地。
- 库里只留：同步状态 `syncStatus`、设备分配的 `user_id`、账号 `__sr<userId>`、有效期。
- 撤销：卡到期 / 退卡走 `del_user`；参观券到期由 `AccessVisitTicketJob`（每 5 分钟）自动清理设备上的人脸。
